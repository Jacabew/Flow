# DS Flow — decisions and assumptions
Jake can veto any of these in the Wednesday session.

- 2026-10-23 · **Own repo** (Jake). Standalone, reusable by DSOS and other builds via API.
- 2026-10-23 · **Jake's time:** Mon + Fri 7:30am 5 min, Wed 8:00am 30 min (Jake; Wed time picked by Claude).
- 2026-10-23 · **Self-managing:** tests are the merge gate; HUB auto-deploys and auto-rolls back. No human clicks (Jake).
- 2026-10-23 · **Zero runtime dependencies**, plain Node 22+ (Claude). Avoids native builds on Windows and supply-chain risk.
- 2026-10-23 · **JSON-file store** instead of SQLite for now (Claude). Volumes are tiny; behind an interface so it can be swapped later.
- 2026-10-23 · **Runs from C:\Flow, not OneDrive** (Claude). OneDrive syncing fights git and live data files. OneDrive\FLOW only gets small status files so Claude can see HUB state remotely. The OneDrive\FLOW\GITHUB folder Jake made isn't needed for running it.
- 2026-10-23 · **Port 5680, bound to 127.0.0.1** (Claude). Not exposed to the internet until a phase needs it (webhooks from the website, phone inbox).
- 2026-10-23 · **Phone alerts via ntfy.sh** (Claude). Free, no account, no subscription. Optional.
- 2026-10-23 · **Deploy task runs as SYSTEM with a read-only GitHub token** if the repo is private (Claude). So it works with nobody logged in.
- 2026-10-23 · **Watchdog alerts once per outage**, not every 5 min, and gives 15 min grace after any restart (Claude). Avoids phone spam and false alarms on deploy restarts.
- 2026-10-23 · **Flows get read access to the store via ctx** (Claude). Needed for system flows (watchdog, daily summary). Flows are repo code, so this isn't a trust boundary.
- 2026-10-23 · **daily.json covers the previous Brisbane calendar day**, written at 00:10 (Claude). If FLOW_STATUS_DIR is unset the flow succeeds and writes nothing. The OneDrive copy of install.ps1 may predate FLOW_STATUS_DIR; refresh it next time the linked computer is available (task added).
- 2026-10-24 · **Archive lives in the data folder** (`C:\Flow\data\archive`), not OneDrive (Claude). Same reason as runs: live data stays out of OneDrive. Archive files are compact JSON, one per Brisbane month; nothing reads them yet.
- 2026-10-24 · **Only finished runs are archived** (Claude). `running` and `waiting_approval` stay live however old, so an approval Jake hasn't answered is never lost.
- 2026-10-24 · **Run cap raised 5,000 → 20,000** (Claude). Heartbeat + watchdog alone make ~580 runs/day, so 5,000 would have deleted runs before the 30-day retention could archive them. The cap is now a safety net only. Added a task to move off whole-file JSON if runs.json grows past ~5 MB.
- 2026-10-24 · **Restart recovery = mark failed + alert, no auto-retry** (Claude). A run cut off mid-step may have half-done a side effect; re-running it blindly could double-send. One alert per stuck run.
- 2026-10-25 · **Default step timeout 5 min** for code/log/if/approval (Claude). Long enough for any real step; short enough that a hung step can't hold a run (and the watchdog) hostage. http keeps its own 30s request timeout; wait steps get their length + 5s.
- 2026-10-25 · **Timed-out work is abandoned, not killed** (Claude). Node can't kill a running promise, so a step that ignores `ctx.signal` may still finish its side effect after the run is marked failed. Connectors that send, pay or write must pass `ctx.signal` through (http already does). No auto-retry beyond the step's own `retries`.
- 2026-10-25 · **Weekly = existing `days` plus a `weekly` shorthand** (Claude). `days` already covered "Mon,Wed 07:30" for one time of day; added `weekly: 'Mon,Wed 07:30'` and day names. No full cron syntax: not needed yet. Multiple times a day = register two flows or add later.
- 2026-10-26 · **Skipped the runs.json size task for now** (Claude). It's conditional on runs.json passing ~5 MB; DS Flow isn't installed on the HUB yet, so there's no file to measure. Revisit once daily.json shows real volumes.
- 2026-10-26 · **/inbox is a static page outside API auth; the key lives only in the phone's localStorage** (Claude). The page contains no data; every read/decision goes through `/api/*` with `x-api-key`, so serving it openly leaks nothing. One shared API key for now; per-device keys can come with the agent registry if needed.
- 2026-10-26 · **Reject asks "are you sure", approve doesn't** (Claude). Approve is the common one-tap action; a mistaken reject silently kills a run.
- 2026-10-27 · **Phone reaches /inbox via a Caddy route on the HUB (`flow.darkspace.au`), not a DSOS proxy** (Claude). DSOS is untouched apart from one Caddyfile block + a DNS record (in DSOS_REQUESTS); DS Flow stays up if DSOS is down; no DS Flow code in DSOS. Only `/inbox`, `/health` and `/api/approvals*` are exposed; DS Flow still binds to 127.0.0.1. Reversible: delete the block. Assumes the HUB's Caddy already does HTTPS for dsos.darkspace.au and the domain's DNS is Jake's to edit.
- 2026-10-27 · **Brute-force guard is in DS Flow, per client IP** (Claude). 10 wrong keys / 15 min → 429. Behind Caddy all traffic is loopback, so the client is the last X-Forwarded-For entry (the one Caddy adds; earlier entries are forgeable). In-memory only, so a restart clears it: acceptable for a long random key.
- 2026-10-27 · **Summary adds `amber` for approvals waiting** (Claude). Brief only said green / X failed; amber tells Jake there's a tap to do without calling it a failure. Red wins when both. Schema frozen: add-only.
- 2026-10-27 · **Mission Control reads the summary server-side, 2 s timeout, grey "no signal" on failure** (Claude). Keeps the API key off the browser and keeps DSOS independent of DS Flow being up.
- 2026-10-28 · **Append-only JSONL log, not SQLite** (Claude). Keeps zero dependencies (node:sqlite is still experimental on Node 22). Did the task before runs.json hit 5 MB: ~580 runs/day x 30 days ≈ 17k runs would pass it in the first month, with the whole file rewritten several times per run. Old .json files are renamed `.json.migrated`, not deleted: if a deploy rolls back, the old code starts with empty history but no data is lost. Nothing is installed on the HUB yet, so in practice there is nothing to migrate.
- 2026-10-29 · **DSOS connector built before the token exists** (Claude). The task said "needs DSOS API key on HUB"; only running it needs the key, so the code and tests (against a fake DSOS) are done now. Without a token a read fails with a clear "not configured" alert; no flow uses it yet. Assumed DSOS auth is `Authorization: Bearer` under `/api/v1` (per the DSOS todos brief) and DSOS listens on 127.0.0.1:3000 on the HUB (per the Sep audit); both overridable by env.
- 2026-10-29 · **DSOS writes need two switches to go live** (Claude): `live: true` in the flow (repo, reviewed) and `FLOW_DSOS_WRITES=live` on the HUB (Jake). Default is shadow: logged in the `shadow` collection (last 5,000), nothing sent. This is the shadow mode CLAUDE.md requires for anything touching money.
- 2026-10-29 · **DSOS writes never auto-retry** (Claude). A timed-out write may have landed; retrying could double it. Reads retry twice like http.
- 2026-10-29 · **Asked DSOS for a scoped, read-only token for DS Flow** (Claude), not the full API token. Write scopes get requested per flow when one needs them (DSOS_REQUESTS #3).
- 2026-10-29 · **Skipped the two "needs the linked computer" Phase 0 tasks** again: this run had no access to the HUB/OneDrive.
- 2026-10-30 · **DS Flow schedules the Xero back-feed; it doesn't do it** (Claude). DSOS already has the Xero OAuth and the back-feed code (D24/D46). Copying either into DS Flow would mean two Xero integrations and two sets of credentials. The shadow week proves DS Flow can own the trigger and the alerting; the sync itself stays in DSOS.
- 2026-10-30 · **"Compare" = did DSOS's own run happen OK each Brisbane day, seen from DS Flow** (Claude). DS Flow can't fetch Xero itself, so it can't diff payment data independently. Ready to switch = 7 matching days in a row (a day DS Flow didn't run counts as a miss).
- 2026-10-30 · **Runs at 08:30 Brisbane** (Claude). DSOS's "daily morning job" time isn't documented anywhere I can read; 08:30 is after any normal morning run. If DSOS runs later, days show `dsos-missed` and the time gets moved.
- 2026-10-30 · **No alert on DSOS misses/failures during the shadow week** (Claude). Shadow = observe only; DS Flow's own failures (bad token, DSOS down) still alert as usual. Alerting on DSOS failures starts at switch-over.
- 2026-10-30 · **Status endpoint shape assumed** `{ lastRunAt, ok, error }` (Claude), with tolerant parsing of common variants. Asked for in DSOS_REQUESTS #4.
